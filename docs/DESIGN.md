# Design — RetroTech

> 제품/기획 의도, UX, 도메인 규칙, 주요 의사결정을 정리한 문서.
> 구조·구성은 [ARCHITECURE.md](./ARCHITECURE.md), 성능은 [PERFORMANCE.md](./PERFORMANCE.md) 참고.

## 제품 개요

**RetroTech** 는 *"기술의 역사를 자세히 설명하는"* 한국어 팟캐스트다. 특정 기술이 어떤 배경에서 등장하고 발전했는지, 또 왜 어떤 기술은 사라졌는지를 다룬다 (예: 2g화 "VCS: SourceForge").

이 웹사이트는 그 팟캐스트의 **허브**다. 역할은 두 가지다.

1. **구독 유도** — 청취자를 각 팟캐스트 플랫폼(Apple/Spotify/YouTube/Google/RSS)으로 보낸다. 사이트 자체가 주 재생 환경은 아니다.
2. **쇼노트/레퍼런스 제공** — 각 에피소드에서 다룬 내용과 출처 링크를 정리해 둔다. 역사·고증 콘텐츠라 레퍼런스 목록이 길고 중요하다(2g화는 참고링크 약 60개).

## 타깃 / 톤

- **한국어 사용자.** `<html lang="ko">`, 한글 우선 폰트 스택, 모든 콘텐츠 한국어.
- 1인 제작(호스트: **Outsider**). 푸터에 호스트 프로필·SNS·후원(GitHub Sponsors) 링크 노출.
- 미니멀한 블로그형 UI. 글 중심의 단순한 외형을 유지하고 군더더기를 더하지 않는다.

## 콘텐츠 구조 & 도메인 규칙

- **에피소드 = 마크다운 파일 1개.** 메타데이터는 프론트매터, 쇼노트는 본문. (스키마: [ARCHITECURE.md](./ARCHITECURE.md#라우팅--콘텐츠-모델))
- **회차 번호 체계:** `시즌 + 알파벳` (`1a`…`1n`, `2a`…). `0` 은 소개 회차. 날짜형 슬러그(`250127-breaks`)는 정규 시즌 외 "쉬어가는" 회차.
- **에피소드 페이지 구성(관례):**
  1. 제목(프론트매터 `title` — 템플릿이 h1 으로 렌더)
  2. 도입 요약 단락(프론트매터 `description` 과 동일 내용)
  3. 구독 배지(`<!--badges-->` 마커 위치, 회차 딥링크는 프론트매터 `badges:`)
  4. `## 레퍼런스:` + 마크다운 링크 목록(빌더가 `.refs` 로 감싸 작은 글씨)
  5. `## 배경음악` 출처 표기(Uppbeat 라이선스 등)
- **레퍼런스는 1급 콘텐츠다.** 역사 고증 특성상 출처(위키, 웹아카이브, 인터뷰, SEC 문서 등)를 충실히 남긴다. `.refs` 는 본문보다 작은 글씨로 처리해 밀도를 높인다.

## 배포 채널 & 구독 (핵심 UX)

사이트의 1차 전환 목표는 "플랫폼 구독"이다. 이를 위한 장치:

- **`internal/builder/badges.go`** — 재사용 가능한 구독 배지 렌더. 기본값은 쇼 전체 링크(채널), 에피소드에서는 프론트매터 `badges:` 로 해당 회차의 딥링크를 넘긴다.
  - Apple Podcasts, YouTube, Spotify 는 항상 노출.
  - **Google Podcasts 는 선택적.** `google` prop 이 있으면 Google 배지를, 없으면 대신 **RSS 배지**(`/feed.xml`)를 노출한다. (Google Podcasts 서비스 종료 이후 RSS 로 대체하는 의도로 해석됨.)
- **RSS 피드가 정식 배포물.** `feed.xml` 은 iTunes 팟캐스트 규격으로 생성되어 Apple 등에 등록되는 실제 피드다. 푸터·`<head>`·홈에서 모두 `/feed.xml` 로 접근 가능.
- 오디오(mp3)는 `retrotech-episodes.outsider.dev` 에 별도 호스팅하고 프론트매터 `enclosure` 로 연결한다(사이트와 스토리지 분리).

## 에피소드 관리 데스크톱 앱 (에디터)

에피소드는 여전히 `content/episodes/*.md` 단일 소스지만, 그 파일을 **손으로 편집하지 않고 폼으로
관리**하는 데스크톱 앱을 둔다. 손이 많이 가던 부분 — `duration` 따옴표(60진수 함정), `enclosure.size`
바이트 계산, 공개 후 채우는 구독 뱃지 5종, 긴 레퍼런스 목록 — 을 폼으로 옮긴다. 구조·구성은
[ARCHITECURE.md](./ARCHITECURE.md#에피소드-관리-데스크톱-앱-retrotech-editor), 상세는
[plan/episode-editor-app.md](./plan/episode-editor-app.md).

- **마크다운을 보지 않는다.** 프론트매터는 폼 필드, 레퍼런스는 행(텍스트+URL+하위 들여쓰기) 편집,
  `<!--badges-->`·`## 레퍼런스:` 스캐폴딩은 합성기가 관리한다. 구조가 특이한 회차만 원문 마크다운으로
  편집(무손실 fallback).
- **번거로움 제거.** 로컬 mp3 를 고르면 `size`·`duration` 이 자동으로 채워진다(파일 업로드 아님 — 두
  값만 읽음). 신규 회차는 id 로 enclosure URL 을 자동 생성한다. 뱃지는 비워두면 쇼 기본값으로
  폴백되므로 "발행 직후 비워두고 나중에 채우는" 기존 워크플로우를 그대로 따른다.
- **초안으로 시작, 발행은 명시적.** "새 에피소드"는 바로 공개되지 않고 **초안**(`content/drafts`,
  사이드바 초안 섹션)으로 시작한다. 초안은 **자동 저장**되어 작업이 유실되지 않고, 사이트·피드엔 보이지
  않는다. **발행**을 눌러야 `content/episodes/<id>.md` 로 기록돼 빌드 대상이 된다(미완성 회차가 실수로
  공개되지 않도록). 발행은 파일만 기록하고 배포(빌드/푸시)는 기존대로 사용자가 별도로 한다.
- **구독자 계약 보호가 최우선.** 수정은 파일 경로의 id 기준이라 URL/guid 가 사고로 바뀌지 않는다.
  합성기는 프론트매터 값을 정확히 보존해 RSS 피드를 바이트 동일하게 유지한다(라운드트립·피드 동일성
  테스트로 증명). 기존 파일을 저장하면 프론트매터 **스타일만** 1회 정규화될 뿐, 값·피드·본문은 불변.
- **참고 앱과 같은 구조를 택한 이유.** `blog.outsider.ne.kr` 의 검증된 패턴(Electron 얇은 셸 + Go
  사이드카 + 임베드 UI)을 그대로 가져와, 작성 도구 자체 기능보다 "앱으로 만드는 구조"를 재사용했다.
- **AI Assist 는 토대만 먼저.** 우측 Assist 사이드바에서 로컬 CLI(Claude/Codex/Gemini)를 골라 프롬프트를
  실행하는 최소 기능을 두고, 구체적인 AI 활용 기능(요약·교정 등)은 이 위에 점진적으로 얹는다. CLI 가
  스스로 인증하므로 앱은 키를 보관하지 않는다.
